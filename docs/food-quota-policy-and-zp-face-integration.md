# کنترل سهمیه غذا و ورود امن پرسنل با چهره

## سیاست مرکزی سهمیه

مدیر از `/Admin/QuotaControl/Index` می‌تواند حالت رزرو آزاد را روشن یا خاموش کند.
در حالت خاموش سهمیه فردی `UnitQuotaPerson` و در حالت روشن، وعده‌های تعریف‌شده
در برنامه غذایی ملاک‌اند. مهلت رزرو و ساعت چاپ ژتون مستقل از این کلید کنترل می‌شوند.

## نتیجه بازبینی امنیت ورود چهره

ورود کاربر ثبت‌نشده فقط پس از **رویداد واقعی و امضاشده ZP که به نشست
مرورگر منتظر همان دستگاه وابسته است** مجاز می‌شود. دانستن شناسه
`enrollId` یا باز کردن URL نمی‌تواند حسابی ایجاد کند یا وارد حسابی شود.

مسیرهای قدیمی `/FaceAuth/LoginByFace` و `/FaceAuth/LoginByFace1`
دیگر ورود مستقیم نمی‌کنند؛ صرفاً صفحه انتظار ZP را باز می‌کنند.
همچنین ورود با نام کاربری و رمز عبور، صرفاً از روی «نام کاربری = رمز =
کد پرسنلی» حساب جدید نمی‌سازد. این رفتار قبلی قابل سوءاستفاده بود.

## قرارداد اجرایی لازم برای سرویس خارجی ZP

**بخش زیر باید در سرور ZP اعمال شود.** این مخزن فقط سمت
سامانه تغذیه را پیاده‌سازی می‌کند؛ بدون اعمال قرارداد در سرور ZP،
ورود خودکار امن عمداً فعال نمی‌شود.

1. مرورگر `GET /Authentication/IndexZP` را باز می‌کند.
2. سامانه تغذیه، چالش ۳۲ بایتی (۶۴ کاراکتر HEX بزرگ) تولید و آن
   را در Session همان مرورگر و cache سمت سرور ثبت می‌کند.
3. مرورگر روی Hub خارجی `/kioskHub` این متد را اجرا می‌کند:

```text
Register(kioskId: int, sessionChallenge: string)
```

   سرور ZP **باید خودِ اتصال کیوسک را احراز هویت کند** و
   `sessionChallenge` را فقط برای همان اتصال معتبر نگه دارد.
   ثبت هر `kioskId` توسط مرورگر دلخواه و بدون احراز هویت، ناامن است.
4. پس از تشخیص موفق چهره، سرور ZP مستقیماً با HTTPS درخواست امضاشده
   زیر را به سامانه تغذیه می‌فرستد. **پیش از دریافت HTTP 200،
   هیچ پیام ورود به مرورگر ارسال نشود.**

```http
POST /Authentication/RecordVerifiedFace
Content-Type: application/json

{
  "kioskId": 1,
  "enrollId": 12345678,
  "timestampUtc": 1793800000,
  "nonce": "unique-cryptographically-random-event-id",
  "sessionChallenge": "64-UPPERCASE-HEX-CHARACTERS-FROM-REGISTER",
  "signature": "HMAC-SHA256-HEX"
}
```

   `timestampUtc` در این مثال ساختگی است؛ هنگام اجرا زمان جاری
   UTC به Unix seconds ارسال شود. رشته‌ای که با کلید محرمانه
   مشترک HMAC-SHA256 می‌شود، دقیقاً عبارت زیر به UTF-8 است:

```text
{kioskId}:{enrollId}:{timestampUtc}:{nonce}:{sessionChallenge}
```

5. سرور تغذیه وجود چالش انتظار، شناسه دستگاه، تازگی زمان
   (حداکثر ۳۰ ثانیه)، امضا، تکراری نبودن nonce و عدم مصرف قبلی
   چالش را بررسی می‌کند. رویداد تا ۴۵ ثانیه قابل استفاده است.
6. پس از دریافت HTTP 200، ZP فقط برای همان اتصال معتبر Hub
   باید یک شیء زیر را بفرستد:

```text
ReceiveAutoLogin({
    enrollId: 12345678,
    sessionChallenge: "same-challenge-from-Register"
})
```

7. مرورگر تطابق چالش رویداد با چالش همان صفحه را بررسی می‌کند و
   فرم امن `POST /Authentication/FinalizeFaceLogin` با
   AntiForgery را ارسال می‌کند. سرور فقط اگر رویداد **یک‌بارمصرف**
   مربوط به **همین Session** باشد اجازه ادامه می‌دهد.
8. سامانه حساب موجود را بازیابی می‌کند یا اگر وجود نداشت از
   سرویس رسمی پرسنلی استعلام می‌گیرد و با شناسه معتبر شخص
   حساب رزروکننده غذا می‌سازد. سپس نشست و توکن Redis ساخته
   می‌شود. شکست Redis نباید نشست نیمه‌کاره معتبر باقی بگذارد.
9. صفحه انتظار قبل از انقضای چالش خودکار تازه می‌شود تا کیوسک
   پس از چند دقیقه استفاده‌نشدن از کار نیفتد.

**نکته درباره اتصال به Hub قدیمی:** اگر ZP فقط
`Register(int kioskId)` یا رویداد `ReceiveAutoLogin(enrollId)`
را پشتیبانی می‌کند، نسخه امن جدید **نباید** با این قرارداد قدیمی
ورود را انجام دهد. لازم است قرارداد فوق به سرویس ZP اضافه شود.
هرگونه بازگرداندن ورود صرفاً با `enrollId` آسیب‌پذیری قبلی
را دوباره فعال می‌کند.

## تنظیمات سامانه تغذیه

در environment variables / تنظیمات امن سرور (نه Git و نه JavaScript):

```text
FaceLogin__WebhookSecret=<high-entropy-shared-secret-min-32-characters>
ApiAddress__KioskId=1
ApiAddress__Refit=https://trusted-zp-service.example
```

اگر کد پرسنلی رسمی با صفر ابتدایی و طول ثابت است می‌توان
`FaceLogin__PersonnelCodeLength` را هم تنظیم کرد؛ در غیر این صورت
این گزینه را حذف کنید تا کد دقیق دریافتی از دستگاه استفاده شود.

`FaceLogin__RequireSignedEvents=false` دیگر مکانیزم امنیتی را
غیرفعال نمی‌کند. **همه ورودهای چهره نیازمند اثبات معتبر هستند.**

کلید webhook هرگز نباید به مرورگر، SignalR client، فایل عمومی
یا مخزن Git منتقل شود. ارتباط webhook و Hub باید HTTPS و
ترجیحاً محدود به شبکه/مبدأهای مورد اعتماد باشد.

## ثبت کاربر جدید و اولین تغییر رمز

**مراد از کاربر جدید، شخصی است که در سامانه تغذیه حساب ندارد اما
دستگاه ZP چهره‌اش را شناخته و `enrollId` معتبر او را ارسال کرده است.**
اگر فرد هنوز در خود ZP ثبت بیومتریک نشده و دستگاه شناسه‌ای برنمی‌گرداند،
این قابلیت نمی‌تواند از تصویر صورت به‌تنهایی کد پرسنلی او را حدس بزند؛
ثبت اولیه در سامانه چهره ZP باید جداگانه انجام شود.


- حساب موجود با `PersonId`، `Username` یا `PersonCode`
  شناسایی می‌شود و بدون ساخت حساب تکراری استفاده می‌شود.
  تناقض صریح هویت و حساب غیرفعال رد می‌شود.
- برای کاربر واقعاً جدید، اطلاعات نام/کد پرسنلی/یگان از
  `GetPersonalByPersonCode` معتبر گرفته می‌شود. نقش پیش‌فرض
  `MealBooker` باید در سامانه فعال و موجود باشد.
- رمز اولیه طبق خواسته فعلی **همان کد پرسنلی** است و
  `PasswordIsChanged=false` ذخیره می‌شود. اگر کاربر بعداً با
  نام کاربری/رمز وارد شود، موظف است رمز را تغییر دهد.
- کد پرسنلی محرمانه نیست؛ امنیت ورود اولیه با این رمزِ قابل‌حدس
  **به‌اندازه کافی بالا نیست**. برای ایمن‌سازی کامل اولین ورود
  با رمز، تأیید دوم مثل OTP به شماره واقعی یا چهره مجدد لازم است.
- شماره موبایل ساختگی از کد پرسنلی تولید نمی‌شود؛ فیلد
  `Mobile` برای این حساب‌ها می‌تواند `null` باشد.

### Migration ضروری

Snapshot قبلی، `Users.Mobile` را `NOT NULL` داشت؛ سرویس
پرسنلی موبایل واقعی برنمی‌گرداند. Migration زیر این ستون را
nullable می‌کند:

```text
20261104190000_FaceLoginNullableUserMobile
```

روی دیتابیس مقصد قبل از فعال‌سازی ثبت خودکار حساب اجرا شود
(با `-Context ApplicationContext`). بدون آن ممکن است ساخت
حساب جدید از SQL خطا بگیرد. برگشت Migration در صورت وجود حساب
بدون موبایل، برای جلوگیری از از بین رفتن داده متوقف می‌شود.

## محدوده اعتبار و نکات استقرار

- `IMemoryCache` برای nonce و اثبات چهره، فقط در **یک نمونه**
  برنامه قابل اتکاست. اجرای چند IIS Worker یا چند Web Server
  نیازمند cache توزیع‌شده همراه با claim اتمیک و اتصال نشست به
  سرور مشترک است. در وضعیت فعلی باید یک نمونه وب فعال باشد.
- سرور ZP باید عضویت Hub را به **اتصال واقعی و مجاز کیوسک**
  محدود کند. صرف دانستن `kioskId` هیچ اثبات هویتی نیست.
- پیش از استفاده عملی، تأیید اتصال ZP، اجرای migration،
  Build و آزمون‌های زیر الزامی‌اند. این موارد فقط با بررسی
  سورس قابل تضمین نیستند.

### سناریوهای پذیرش

1. کاربر تعریف‌نشده، چهره معتبر، رویداد امضاشده، پرسنل معتبر:
   حساب جدید ایجاد و وارد شود؛ Username = کد پرسنلی.
2. همان فرد برای بار دوم: حساب تکراری ایجاد نشود.
3. حساب غیرفعال یا PersonId متناقض: ورود رد شود.
4. `GET FinalizeFaceLogin` و URL جعلی: ورود نکنند.
5. webhook با HMAC اشتباه، زمان منقضی یا nonce تکراری: رد شود.
6. مرورگر دوم با همان `enrollId` و Session دیگر: ورود نکند.
7. پیام SignalR بدون `sessionChallenge` یا با چالش اشتباه: رد شود.
8. در صورت قطعی API پرسنلی: حساب جدید ساخته نشود.
9. در صورت قطعی Redis: نشست نیمه‌کاره ورود باقی نماند.
10. ورود با کد پرسنلی/رمز در صورت نداشتن حساب: حساب تازه نسازد.
11. ورود با رمز اولیه پس از ایجاد حساب: تغییر رمز الزامی باشد.
12. کیوسک که بیش از ۳ دقیقه باز بوده: چالش انتظار خودکار تازه شود.

## بخش‌های خارج از این تغییر

- QR یک‌بارمصرف تحویل غذا برای رزروهای جدید هنوز پروژه جداگانه‌ای
  است و نباید با تأیید ورود چهره اشتباه گرفته شود.
- اتصال سرویس **خارجی** ZP در مخزن سامانه تغذیه وجود ندارد؛ تغییر
  قرارداد ZP باید در همان سرویس واقعی اعمال و با دستگاه تست شود.
